# Demo script

A three minute walkthrough. The timings assume you have already installed the
package and copied `.env.example` to `.env`. Nothing here requires an LLM key
except the optional Slack segment.

Rehearse it once. The commands are fast, but the plan table is dense and you
want to know which two rows you are pointing at.

---

## Before you start

```bash
./.venv/bin/python -m pytest tests/ -q      # should print 8 passed
```

Have two terminal tabs open. Tab 1 for the CLI, tab 2 for the Streamlit UI if
you plan to show it.

Clear old artifacts so the run you demo is unambiguous:

```bash
rm -rf runs/
```

---

## Beat 1: the problem (20 seconds, no terminal)

One sentence, said out loud while the plan table is still off screen:

> A GDPR erasure request arrives as one email address. The obligation is to
> find every copy of that person across the warehouse. Teams do this by hand
> today, and the fines are for the copies they miss.

Do not read the fine table from the README. It is there for the judges to read
later.

---

## Beat 2: the plan (45 seconds)

```bash
./.venv/bin/erase plan --email priya.sharma@example.com --fixtures
```

Nine assets come back, each with an action and a reason. Point at exactly two
rows:

**The dbt model, `staging.patients_clean`.** The action is `dbt_rerun`, not
`delete_row`. Say why: deleting rows out of a dbt model is wrong, because the
next scheduled run would rebuild them from the source. The correct move is to
anonymize the source and rebuild. That distinction is the difference between an
erasure that holds and one that silently reverts.

**The sandbox table, `analytics_sandbox.priya_analysis_2024`.** The action is
`residual_review` and it is flagged, not actioned. Say why: it has no owner and
no PII tag. A static PII catalog does not know it exists. It only shows up
because we walked lineage at request time, and Vismriti refuses to generate
destructive SQL for an asset nobody can vouch for.

That second row is the whole argument for the product. Give it a beat.

---

## Beat 3: nothing runs without a human (30 seconds)

```bash
./.venv/bin/erase run --email priya.sharma@example.com --fixtures --approve --dry-run
```

Then open the generated report:

```bash
cat runs/*.md | head -40
```

Points to make while it scrolls:

- The SQL was generated by templates in the planner, not by the language model.
  The model chooses which tool to call; it never composes a `DELETE`.
- Destructive tools are gated on explicit confirmation. `--approve` on the CLI
  is that confirmation made explicit for a scripted demo. In the service, the
  same gate is an approval click.
- Advisory actions, the dbt rerun and the dashboard invalidation and the model
  retrain flag, are reported as advisory. Vismriti annotates them; it does not
  claim to have performed work in systems it does not touch.

## Beat 4: live metadata (30 seconds)

```bash
./.venv/bin/python scripts/verify_live_datahub.py
```

Shows GMS version and the seeded entities read straight off the live instance,
no auth, reproducible from any laptop. Then:

```bash
./.venv/bin/erase plan --email priya.sharma@example.com
```

Same pipeline, live metadata instead of fixtures.

If a judge asks about the write-back: answer directly. The reference DataHub
deployment runs without Kafka, so aspect ingestion cannot land, and the
execution report says so explicitly rather than reporting a success that did
not happen. The durable audit artifact in that configuration is the JSON and
Markdown pair under `runs/`. Against a DataHub with Kafka, the same code path
writes the annotations and the `erasureRequest` entity. This is a deployment
limitation, not a missing feature, and being straight about it is worth more
than a green checkmark that lies.

## Beat 5: the interfaces (25 seconds)

Tab 2:

```bash
./.venv/bin/streamlit run src/vismriti/ui/app.py
```

Show the report rendering. Then state, without demoing each one, that the same
orchestrator is reachable four ways: the CLI you just used, the HTTP API, this
UI, and Slack. The orchestrator itself contains no LLM calls, which is why the
deterministic path can be unit tested offline.

If you have Slack wired and time left:

```
@vismriti erase priya.sharma@example.com
```

and click one approve, one reject. The split decision is the point. Approval is
per action, not all or nothing.

---

## Beat 6: close (10 seconds)

> One email in. Every downstream copy found, including the one no catalog knew
> about. A plan a human approves action by action, and an audit trail that
> records what actually happened, including what failed.

## Questions you should expect

**Does the model write the SQL?** No. Templates in `services/planner.py`
generate it from deterministic rules. The model selects tools and explains
results. Identifiers coming from metadata are validated before they reach a
template, and anything that fails validation becomes a residual-review item
instead of SQL.

**What stops the agent deleting something on its own?** The destructive tools
require confirmation at the framework level, so the run halts and waits for a
decision. Dry-run is on by default on top of that.

**Why is that sandbox table residual instead of deleted?** Because no owner
means no one can confirm what depends on it. Guessing is how you break a
downstream report, and a wrong delete is not reversible.

**How does this differ from DataHub's built-in features?** DataHub tells you
what exists and how it connects. Vismriti turns one subject identifier into an
executable, approvable, auditable erasure plan across that graph, and flags the
untagged residuals that tag-based tooling structurally cannot see.

**Is it production ready?** Be honest about the current state: the
deterministic core is tested, the approval gate is real, and the write-back
reports failure truthfully. Point at `SETUP.md` for the deployment model that
keeps warehouse credentials out of the agent.
